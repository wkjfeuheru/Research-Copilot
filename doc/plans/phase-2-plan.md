# 第二阶段：逐个开发研究 Agent，首批实现 Planner

日期：2026-10-22  
状态：已实施；验收记录见 [phase-2-verification.md](phase-2-verification.md)。  
需求依据：[项目规格](../spec.md)

## 开发方式

参考原项目的职责划分，按 **Planner → Data Fetcher → Analyst → Risk Checker → Writer → 交付检查** 逐个开发。每批完成节点契约、实现和测试后再进入下一批；条件路由在相关节点具备后接入。

本次只实施 **Planner（研究规划 Agent）**，不编写基线差异报告，也不一次性搭建整条研究链路。

## 首批实施内容

### 1. 定义 Planner 输入输出契约

使用 Pydantic 定义独立输入、输出模型并导出 JSON Schema。

输入包含：研究问题、A 股市场范围、可选截止日期、用户选择的技能标识、附件元信息，以及人工补充说明。此阶段不读取附件正文、不执行技能。

输出包含：

- 研究对象与问题类型：个股、行业或公司对比。
- 研究目标、分析维度及明确采用的假设。
- 数据需求：所需指标、资料类型、时间范围及用途。
- 执行步骤及所需能力。
- 待澄清问题和规划状态：`ready`、`needs_clarification`、`unsupported`。

无法确定的股票代码或日期不由模型自行补造；保留待解析对象或提出澄清。规划步骤描述研究意图，实际执行顺序由后续 LangGraph 编排控制。

### 2. 实现 Planner 与模型调用边界

- 在现有 `agents/` 中实现 Planner，在 `llm/` 中定义最小结构化模型调用接口。
- 通过依赖注入传入模型客户端；本批用测试替身验证 Planner，不预先绑定尚未确定的模型供应商。
- 提示词要求规划围绕证据获取、分析、风险核查和报告产出，并输出规定结构。
- 程序校验输出 Schema，以及必填内容、步骤引用、技能标识是否来自输入。
- 模型调用失败与结构校验失败明确返回错误；不自动生成默认计划、不静默转 mock，不在本批增加自动修复循环。

### 3. 建立最小 LangGraph 集成

只建立 `START → Planner → END` 的单节点图，验证输入转换、节点调用与结果保存。

`needs_clarification` 作为规划结果返回；跨请求人工恢复、checkpoint 和研究任务生命周期留待后续批次实现。本批不添加空壳 Data Fetcher 或模拟报告节点。

### 4. 文件与界面边界

主要修改现有后端 `agents/`、`llm/`，新增最小状态与编排模块，以及对应测试。计划和验收记录放入 `doc/plans/`。

不新增研究 HTTP 接口，不修改前端发送行为，不连接数据库、MCP、搜索或长期记忆。测试替身仅存在于测试目录，不进入生产默认路径。

## 验收标准

- 个股财务质量、行业研究、三家公司对比三类问题均可形成合法规划结果；测试结果明确属于固定模型响应下的程序验证。
- 问题含糊时返回待澄清结果；超出 A 股研究范围时返回不支持结果。
- 非法 JSON、缺失字段、无效步骤引用和未知技能标识均被拒绝。
- 模型调用异常可追踪，不被伪装为规划成功。
- 单节点图输出与直接调用 Planner 的结果一致。
- 现有健康接口和配置测试继续通过。
- 验收记录明确：本批验证节点结构与控制逻辑，不代表真实模型规划质量已验收。

## 后续节点顺序与默认边界

Planner 验收后，下一批单独设计 Data Fetcher 的输入输出和数据接入；随后依次实现 Analyst、Risk Checker、Writer 与交付检查。每批先明确范围，再编码。

本批默认不进行付费调用。真实模型适配与规划质量验证在供应商、模型和调用预算明确后补充；不因接口已定义就宣称 Planner 已具备真实研究能力。
